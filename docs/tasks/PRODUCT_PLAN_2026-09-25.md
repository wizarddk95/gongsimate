# 국내 공시 리서치 에이전트 — 제품 계획 및 TASK-003 검토

작성일: 2026-09-25

이 문서는 대화에서 확인한 요구사항과 사용자가 제공한 TASK-003 작업 로그·README를 종합한 계획이다. 저장소 코드와 실제 ZIP을 직접 검사한 코드 리뷰가 아니다. 테스트 결과는 에이전트가 보고한 결과이며 독립적으로 재실행하지 않았다. 미확정 제안을 확정 정책으로 취급하지 않는다.

## 1. 이번 판단

TASK-003의 기본 방향은 적절하다. 수집된 원본 버전을 고정하고, 네트워크 호출 없이 문서 요소를 만들며, 표의 병합 구조와 출처를 보존하는 것은 이후 검색과 근거 인용에 필요한 작업이다. 수집의 전체 시장 배치 기능을 완성하기 전에 이 작업을 진행한 것도 적절하다.

다만 다음 두 가지는 청킹 전에 확인·보완한다.

1. XML 전처리가 알 수 없는 구조를 일반 텍스트로 바꾸어 누락이나 의미 변형을 성공으로 숨기지 않는가.
2. 전처리 이후 같은 트리에서 locator를 다시 찾는 검증 외에, 원본 내용과 추출 결과를 독립적으로 대조했는가.

완료 결과의 재사용 검증과 다음 단계의 `partial` 처리 규칙도 이때 명확히 한다. 전면 재작성은 필요하지 않다. 문서에 설명이 없다는 이유만으로 구현 결함을 단정하지 않고, 이미 충족한 항목은 근거를 기록한다.

## 2. 제품 목적과 사용자

### 확정된 방향

- 주 사용자: 공시를 직접 읽고 기업을 분석하는 개인 투자자.
- 보조 사용자: 기업 분석 업무를 수행하는 실무자.
- 제공하려는 가치: 자연어 질문을 기업 공시의 근거와 연결해 분석 시간을 줄이고, 사용자가 답변을 원문에서 확인할 수 있도록 한다.
- 장기 사업 목표: 인수 가능성을 포함한 제품 사업화. 후원과 기업 광고도 고려한다. 네이버 인수는 희망하는 결과이며 현재 검증된 사업 가정은 아니다.
- 개발 과정에서 의사결정, 실패 사례, 평가 결과, 비용과 운영 경험을 포트폴리오로 정리한다.

### 첫 기능으로 권장하는 범위

“기업의 실적이 왜 변했는지 공시 근거로 설명하고, 관련 사업·위험 요인을 후속 질문으로 확인한다.”

처음부터 모든 투자 판단과 수치 계산을 처리하지 않는다. 수치 비교는 기간·통화·단위·연결/별도 구분을 검증할 수 있는 범위부터 확장한다. 공시에 원인이 없으면 외부 지식으로 메우지 않고 근거 부족을 알린다.

성공 기준은 답변 생성 자체가 아니라 사용자가 근거를 확인하고 분석에 활용할 수 있는가이다. 장기적으로는 재방문과 실제 활용도도 확인한다.

## 4. 사용자 여정과 시간 해석

1. 사용자가 “삼성전자의 실적 변동 이유를 보고 싶어”라고 질문한다.
2. 에이전트가 기업을 식별하고 분석 기간이 충분히 명확한지 판단한다.
3. 명확하면 해석을 표시하고 진행한다. 모호하면 필요한 사항을 묻거나, 정해진 기본 기간을 제안하고 그 가정을 표시한다.
4. 공시 근거가 필요하면 검색 도구를 호출한다. 이미 대화에 충분한 근거가 있으면 재사용할 수 있다.
5. 답변에 분석 기간과 출처를 제시한다. 사용자는 해석을 수정하거나 후속 질문을 한다.

“삼성전자”만으로 사업연도 2025가 논리적으로 확정되지는 않는다. 기본 기간 정책을 정하면 제안할 수 있지만 사용자 발언에서 추출한 값과 구분해야 한다.

시간 필드는 다음처럼 역할을 분리한다.

| 필드 | 의미 | 처리 방향 |
| --- | --- | --- |
| target_period | 사용자가 분석하려는 실적·사건의 기간 | 사용자 발언, 대화 맥락, 명시한 기본값에서 도출. 모르면 비워 두거나 확인 |
| report_fiscal_year | 문서가 다루는 보고 사업연도 | 문서·메타데이터의 근거로 추출하고 불확실하면 미상 유지 |
| receipt_date | 공시 접수일 | 발견 API의 기간 조건. 사업연도와 별개 |
| as_of | 어느 시점까지 알려진 자료를 사용할지 | 과거 시점 분석 시 별도 제약으로 적용 |

사용자나 LLM이 “2024년 사건의 설명이 2025년 보고서에 있다”는 사실을 미리 알아야 검색할 수 있는 구조를 만들지 않는다. 검색 도구는 대상 기업과 분석 기간을 받아 관련 문서를 넓게 찾고, 문서 기간·접수일·본문 근거를 이용해 후보를 좁힌다. `target_period=2024`를 그대로 `report_fiscal_year=2024` 하드 필터로 복사하지 않는다. 과거 시점 분석에서는 그 시점 이후 공시의 사용을 별도로 막아야 한다.

### 수집 정책

- 기업·기간으로 접수번호를 발견한다. 접수번호는 발견 이후 개별 공시를 식별하는 키다.
- 원격 동기화는 로컬 정상 여부와 무관하게 다시 다운로드해 검증한다.
- HTTP 성공과 정상 ZIP 여부는 별개다. 정상 검증된 바이트만 원본 버전으로 취급한다.
- SHA-256은 내용 비교와 버전 식별에 사용한다. 공시 자체의 식별자는 접수번호다.
- 바이트가 달라지면 이전 버전을 유지한다. ZIP 해시 변화만으로 본문 정정을 단정하지 않는다.
- 실패 시 마지막 정상 원본과 마지막 성공 확인 시각을 보존한다.
- 최신성은 해당 실행의 성공한 DART 응답과 일치한다는 의미다. 지속적 최신성이나 시장 전체 동일 시점 스냅샷을 주장하지 않는다.
- 별도 접수번호의 정정공시는 별도 공시다. 향후 정정 관계와 시점별 사용 정책이 필요하다.

### 파싱 정책

- 저장된 ZIP 버전을 시작 시 한 번 고정한다. 실행 중 원격 조회나 current 추적을 하지 않는다.
- 원본과 파생 결과를 분리하고 원본은 수정하지 않는다.
- 제목·문단·표를 보존한다. 셀 병합 값을 여러 칸에 복제하거나 표 안 문장을 본문에 중복 생성하지 않는다.
- 문서 역할이나 사업연도를 근거 없이 추정하지 않는다. unknown은 허용한다.
- locator는 특정 전처리와 파서 버전의 트리 위치다. 원본 바이트 위치·페이지 번호라고 표현하지 않는다.
- 이미지·미지원 문서·누락과 경고를 기록한다. 읽지 못한 텍스트를 단순 제외로 숨기지 않는다.
- 원문 요소는 보존하고 검색용 정리·필터링은 이후 버전이 있는 별도 변환으로 수행한다.

### 에이전트 정책

LLM은 직접 답변, 추가 질문, 검색, 추가 검색, 기존 근거 재사용, 근거 부족 안내, 정책상 거부 중 필요한 동작을 선택한다. 서버는 도구 인수, 데이터 접근 범위, 호출·비용 한도를 검증한다.

검색 최대 2회·LLM 최대 4회는 과거 초기 제안이며 고정된 제품 정책이 아니다. 호출 한도는 비용뿐 아니라 무한 반복과 지연을 막는 실행 경계다. 평가를 통해 조정하고 한도 도달 시 확보한 근거와 한계를 알리는 동작을 정한다.

불법·유해 요청의 거부와 공시 근거 부족에 따른 답변 보류는 별도 유형으로 평가한다. 법률이나 민감한 주제를 언급했다는 이유만으로 모두 거부하는 정책은 확정하지 않았다.

## 6. 현재 구현 상태와 TASK-003 검토

### 보고된 상태

- 단건·기업 기간 수집: 앞선 여섯 완료 조건을 코드와 테스트 기준으로 통과했다고 보고됨. 원본 변경과 장애 일부는 모킹 검증이고, 실 API에서는 unchanged 관측.
- 파싱: 34개 테스트 및 `ruff check src tests` 통과 보고. 이수페타시스의 사업·분기·반기 보고서 세 건에서 성공 보고.
- 표본: 사업보고서는 2025 사업연도, 분기·반기는 2026 기간. 파서 형식 검증 표본으로 적절하나 2023~2025 시장 범위 수집 완료를 뜻하지 않음.
- 25개 locator 대조: 위치 재현 검증의 근거다. 전처리 전 원문 보존과 추출 누락의 독립적인 검증 여부는 추가 확인 필요.
- 청킹, 검색 인덱스, 에이전트, 로그인, 실제 서비스 운영은 제공된 자료에서 완료를 확인하지 못함.

| 우선순위 | 항목 | 판단과 요청 |

## 7. 평가와 사용자 스토리 작성 방식

질문을 먼저 만드는 방식과 원문을 먼저 읽는 방식을 함께 쓴다.

1. 사용자 관점: 실제 분석 목적에서 질문을 작성한다. 검색 가능한 질문만 만들지 말고 모호함·자료 부족·기간 혼동도 포함한다.
2. 원문 관점: 실제 공시에서 근거를 고르고, 표·문장·정정·기간 등 놓치기 쉬운 구조를 테스트한다.
3. 결합: 질문에 대한 근거가 실제 존재하는지 사람이 확인하고 기대 동작을 정한다. LLM 초안은 검수 전 정답으로 취급하지 않는다.

평가 근거는 먼저 원본 버전과 문서 요소에 연결한다. 청크 ID에만 묶으면 청킹 변경 때 평가 기준도 흔들린다.

유형은 무한히 열거하기보다 사용자 가치, 발생 빈도, 실패 피해, 구현 변경의 영향을 기준으로 고른다. 초기에는 대표 질문 10~20개와 파서의 위험 구조 표본부터 시작하고 실제 실패·피드백을 회귀 평가로 추가한다. 이는 초기 제안 수량이며 전체 품질을 보장하는 표본 수가 아니다.

운영자의 실패 확인·재처리도 사용자 스토리에 포함한다. 투자자의 분석 여정과 운영자의 복구 여정을 나누어 관리하면 된다.

평가는 수집 범위 → 파싱 충실도 → 검색 근거 회수 → 도구 선택 → 답변 근거 일치 → 비용·지연 순으로 원인을 분리한다. 처음부터 하나의 종합 점수만 만들지 않는다.

### 1. XML 전처리의 안전성과 추적 가능성

- 현재 “알려진 태그 밖의 `<`와 bare `&`를 이스케이프”하는 구현을 검사하세요. 알 수 없는 정상 태그를 일반 텍스트로 바꾸고 success로 처리하는 경로가 있는지 확인하세요.

## 11. 계획 관리 원칙

확정 요구사항의 변경은 최신 사용자 결정에 따른다. 이 문서의 “권장·제안·미정”은 승인된 요구사항으로 자동 승격하지 않는다. 이후 작업마다 변경된 정책과 이유만 짧게 기록하고, 전체 계획서는 큰 방향이 바뀔 때 갱신한다.

포트폴리오에는 현재 수준을 “운영급 서비스를 목표로 수집·파싱 기반을 구현하고 검증 중”으로 기록한다. 실제 운영·전체 시장 지원·완전한 원문 보존을 아직 달성하지 않았다면 달성했다고 표현하지 않는다.
