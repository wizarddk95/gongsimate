# Cursor 전달용: 파서 잔여 결함 보완 및 표 단위 처리

아래 전체 내용을 작업 지시로 사용한다. 사용자가 제공한 코드 리뷰에 근거한 요구사항이며, 현재 저장소 구현을 직접 확인한 결과는 아니다.

## 목표와 진행 방식

저장소 지침, parsing.py, run_parse_cli, 관련 테스트와 최신 작업 로그를 읽고 아래 요구사항을 실제 구현에 대응시키세요. 먼저 변경 계획을 docs/worklog에 짧게 기록한 뒤 구현·검증까지 진행하세요. 일반적인 구현 선택은 스스로 결정하고, 요청 범위와 충돌하거나 기존 데이터를 훼손해야 할 때만 질문하세요.

이전 리뷰의 2번(병합 범위 제한), 3번(셀 안의 여러 중첩 표 연결)은 해결되었다고 보고됐습니다. 해당 수정과 테스트를 확인·보존하되 재설계하지 마세요. 이번 범위는 1번 제목 계층, 4번 전역 locator 상태, 5번 동시 쓰기, 6번 CLI 상태 표시입니다. 표 단위는 아래 제한된 방침을 적용합니다.

## 유지할 계약

- 파서는 네트워크를 호출하지 않고 입력 원본 SHA를 시작 시 고정합니다. 원본 ZIP·수집 current·수집 로그는 수정하지 않습니다.
- 원본과 이전 파싱 결과를 보존합니다. 출력·설정·변환 동작 변경 시 파서/스키마/설정 버전 식별을 갱신하여 구버전 캐시가 새 결과로 재사용되지 않게 합니다.
- COMPLETE는 산출물 공개 완료입니다. overall_status와 search_eligible은 별개입니다. 기존 검색 계약은 success만 수용하며 partial은 제외합니다.
- 출력이 결정적인 경우 같은 입력·버전·설정의 요소와 ID는 같아야 합니다. 스레드 실행 순서가 영향을 주면 안 됩니다.
- 미지원 태그의 제목 경로를 개선하는 것만으로 해당 태그가 지원된 것으로 취급하거나 partial을 success로 승격하지 않습니다.

## A. 전역 _PATHS 제거 — 리뷰 4번

- locator 경로 맵을 파싱 호출 또는 문서 트리별 컨텍스트로 옮기세요. 전역 mutable 상태, 스레드별 임시 전역으로 문제를 우회하지 마세요.
- parse_receipt, resolve_locator, element_text_at이 다른 호출의 상태에 의존하지 않도록 하세요. 기존 API 호환 여부를 명시하세요.
- 컨텍스트는 올바른 원본·ZIP 멤버·트리에 묶여야 합니다. 같은 이름의 다른 멤버도 구분합니다.
- 두 문서의 처리를 의도적으로 교차 실행해도 각 locator가 해당 문서의 정확한 노드를 가리키는지 검증하세요. 단순히 예외 없이 끝나는 것만 확인하지 마세요.

## B. 미지원 태그 내부 제목 계층 — 리뷰 1번

- 알려진 컨테이너와 미지원 래퍼를 순회할 때 제목 컨텍스트 전달이 어떻게 다른지 작은 fixture로 재현하세요.
- 검증된 SECTION 구조와 TITLE 관계에 대해서, 미지원 래퍼 안에서도 후속 문단·표에 올바른 section_path가 전달되도록 순회 책임을 정리하세요.
- 자식의 제목 컨텍스트가 래퍼 밖의 무관한 형제나 다음 문서로 새지 않도록 범위를 정의하세요. 각 재귀 호출 결과를 전역 경로에 무조건 이어 붙이지 마세요.
- 구조 의미가 불확실한 경우 계층을 새로 추정하지 말고 알려진 경로와 경고를 보존하세요. <CORRECTION> 정식 지원은 이번 범위 밖이며 해당 문서는 partial을 유지합니다.
- fixture: 부모 제목, 래퍼 내부 제목과 문단, 중첩 SECTION, 래퍼 뒤 형제 문단을 함께 넣어 기대 경로를 명시하세요. 실제 정정본을 사용할 수 있으면 원문과 대조하되 정정본이 검색 가능해졌다고 보고하지 마세요.

## C. 파서 결과 동시 쓰기 — 리뷰 5번

- 수집 lock을 그대로 공유하지 말고 파서 산출물 경로에 대한 동시 쓰기를 보호하세요. 대상은 로컬 파일시스템이며 분산 락은 이번 범위 밖입니다.
- 잠금 범위에는 기존 결과 검증, 손상본 격리, 재사용 판단, 결과 공개 등 같은 경로를 변경하는 작업이 포함돼야 합니다. 구현 복잡성을 줄이기 위해 해당 산출물 생성 전체를 잠가도 됩니다.
- 경로가 config hash 앞 16자를 사용한다면 동일 실제 경로에 대한 잠금이 충돌을 막아야 합니다. 전체 해시가 다른 경우 기존 충돌 오류 정책을 유지하고 덮어쓰지 마세요.
- 대기 후 잠금을 얻은 작업은 결과를 다시 검증하고 정상 완료본을 재사용하세요. 무한 대기하지 말고 시간 초과를 별도 오류로 반환하세요. lock 대기 실패가 원본 손상이나 파싱 실패인 것처럼 기록되지 않게 하세요.
- 프로세스별 고유 임시 디렉터리를 사용하세요. 다른 실행의 .tmp-*나 완료 결과를 지우지 마세요. 실패 시 자기 실행이 소유한 임시 산출물만 정리합니다.
- 강제 종료 후 남은 임시 디렉터리의 자동 정리는 필수 아님을 명시하세요. 오래됐다는 이유만으로 타 실행의 lock을 삭제하지 마세요. 잠금 해제·잔여물 처리 규칙을 문서화하세요.
- Windows/PowerShell + uv 환경을 고려해 잠금 방식을 선택하세요. 선택 이유와 지원 파일시스템 범위를 설명하고, 검증하지 않은 OS에서 테스트했다고 주장하지 마세요.
- 실제 다중 프로세스 테스트로 동일 대상 경합을 재현해 정상 완료본 하나가 공개되고 후속 호출이 재사용하는지 확인하세요. 중단된 임시 결과는 COMPLETE 결과로 인식되지 않아야 합니다. 테스트는 시간 제한을 둡니다.

## D. CLI 진단 정보 — 리뷰 6번

- 기존 종료 코드 계약(형식 오류 2, failed/unsupported 1, success/partial 0)을 유지하세요. partial만 다른 종료 코드로 바꾸는 것은 이번 변경에 포함하지 않습니다.
- 출력 앞부분에서 status와 search_eligible을 명확히 구분하세요. partial이면 '처리 완료, 검색 입력 제외'라는 의미가 드러나야 합니다.
- source_sha256, parser_version, preprocess_version, config_hash, reused, manifest 경로를 표시하세요.
- 멤버별 상태와 주요 경고/오류 코드를 요약하세요. 정상 패키지에도 비치명적 경고가 있으면 볼 수 있어야 합니다. 큰 경고 목록은 개수와 생략 여부 및 상세 파일 경로를 표시하세요.
- 문서 본문 전체나 불필요한 민감정보를 출력하지 마세요. 신규 결과와 재사용 결과에서 같은 진단 계약을 유지하세요.
- manifest가 품질 상태의 기준이며 사람이 읽는 CLI 문구를 파싱해 검색 자격을 결정하지 않는다고 문서화하세요. JSON 출력이 이미 있으면 같은 필드를 반영하고, 없으면 이번에 반드시 새 CLI 옵션을 추가할 필요는 없습니다.

## E. 표 단위 방침 — 원문 보존과 해석 분리

결정: 원문 셀·문단은 그대로 보존합니다. '(단위: 원)'을 숫자로 변환하거나 주변 모든 표에 적용하지 않습니다. FinancialFact, 계정 매핑, 단위 환산은 이번 범위 밖입니다.

이번에 할 일:

1. 실제 원본에서 단위 표현이 표 안 셀, 앞선 별도 문단, 별도 레이아웃 표, 혼합 단위 표에 나타나는지 관측한 범위만 기록하세요.
2. 현재 요소/셀 텍스트와 locator만으로 단위 표현을 재현할 수 있으면 그것을 우선 활용하세요. 필요한 경우 unit_mentions 같은 최소한의 관측 레코드를 추가하되 raw_text와 source element/cell locator를 보존하세요.
3. 단위 문자열 발견과 적용 범위 확정은 별도입니다. 표 안에 있다는 이유만으로 표 전체 단위라고 확정하지 마세요. '(단위: 백만원, %)'는 하나의 배수로 표현하지 않습니다.
4. 행·열·개별 셀·표 전체 중 적용 범위가 명시적으로 입증된 경우에만 해당 관계를 기록합니다. 규칙과 근거를 남기고, 모호하거나 상충하면 unresolved/conflict 등 명시적인 상태로 둡니다. 모든 칸에 임의의 기본 단위를 채우지 마세요.
5. 표 밖의 단위를 단순 인접성으로 자동 연결하지 마세요. 별도 요소로 보존하고 적용 대상은 미상으로 둬도 됩니다. 부재와 판정 실패를 구별하세요.
6. 청킹 단계에서 단위 근거를 문맥으로 함께 실어야 한다는 계약을 문서화하세요. 실제 청커는 구현하지 않습니다. unit_mentions를 추가하더라도 미확정 단위를 확정 재무 사실로 취급하지 않습니다.

범위를 키우지 않기 위해 단위의 완전한 의미 해석기는 만들지 마세요. 새 스키마가 불필요하다면 현재 필드로 보존되는 예시와 후속 연결 계획만 제출해도 됩니다. 추가하면 혼합 단위·표 밖 단위·미상 범위를 검증하는 작은 테스트를 포함하세요.

- 해당 변경을 겨냥한 회귀 테스트, 기존 테스트, 프로젝트의 lint를 실행합니다.
- 기존 실원본 표본을 재검증할 수 있으면 동일 요소 내용과 예상 변경된 section_path 등을 구분해 비교합니다. 새 버전 때문에 ID가 달라진 것과 내용 손실을 구별하세요.
- 파서 캐시 재사용의 파일 무결성 검증이 무엇인지 정확히 기록합니다. 줄 수 확인만으로 동일 길이 내용 변조까지 검출한다고 주장하지 마세요. 이번 범위 밖의 추가 결함은 영향과 함께 남깁니다.
- README와 작업 로그에 수정 사항, 실제 검증 범위, 남은 제약, 버전 변경·재처리 필요 여부를 기록합니다.
- 사용자에게는 (1) 무엇이 달라졌는지 (2) 수정 전후 작은 예시 (3) 테스트 결과 (4) 기존 결과를 어떻게 다룰지 (5) 남은 한계를 짧게 보고하세요.
- 최종 평가 데이터에 element_id를 고정하기 전 새 파서 버전으로 대상 공시를 다시 처리하세요. 초안 질문 작성은 병행 가능합니다.

청킹·검색·평가셋 정답 생성, 원격 재수집, 수집 복구 기능 확장은 이 작업에 추가하지 않습니다.
