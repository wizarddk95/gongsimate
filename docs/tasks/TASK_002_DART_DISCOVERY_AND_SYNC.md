# TASK-002 — 공시 자동 발견과 DART 원본 재확인 동기화

아래 내용을 Cursor 코딩 에이전트의 작업 지시로 사용한다. 현재 저장소를 확인하고 구현을 진행하라. 이 지시서 자체는 기존 구현의 완료나 테스트 통과를 증명하지 않는다.

## 1. 목표와 협업 방식

사용자는 Cursor·uv·GitHub을 사용한다. TASK-001의 접수번호 한 건 원본 수집 기능을 기반으로 다음을 구현한다.

1. 기업과 접수일 범위로 공시 목록을 조회해 접수번호를 자동으로 발견한다.
2. 기존 파일이 정상이어도 DART 원본을 다시 받아 비교한다.
3. 원본이 같으면 중복 저장하지 않고 원격 확인 이력을 갱신한다.
4. 달라졌으면 기존 원본을 보존하고 새 버전을 현재 관측 원본으로 지정한다.

사용자는 코드 상세 검토를 이후 코딩 에이전트와 진행한다. 이번에는 작은 기술 선택마다 질문하지 말고 저장소 관례에 맞춰 구현하라. 파일 구조·함수·클래스 설계는 에이전트가 결정한다. 제품 범위·데이터 보존·비용·비밀정보 처리 원칙을 바꾸어야 할 때만 쟁점을 설명하라.

먼저 Git 상태, 프로젝트 지침, TASK-001 구현과 테스트를 확인한다. 기존 사용자 변경을 덮어쓰지 않는다. TASK-001이 미완성이면 필요한 기반부터 완성한다. 이번 요청은 새로운 저장소를 다시 만드는 요청이 아니다.

## 2. 이전 계약에 대한 명시적 변경

TASK-001의 다음 정책은 이번 작업부터 폐기한다:

- 로컬 정상 파일이면 네트워크 없이 skipped 처리.
- 정상 로컬 파일이 있으면 API 키 없이 수집 성공 처리.
- 원격 refresh는 후속 작업이라는 제한.

새 기본값은 온라인 재확인이다. 단일 접수번호 CLI와 목록 기반 수집 양쪽에 적용한다. 로컬 검증만 하는 기능이 남아 있어도 'DART 최신 확인 완료'라고 표시하면 안 된다. API 키가 없거나 원격 조회에 실패하면 원격 확인 실패이며, 기존 파일이 있다는 이유로 성공으로 바꾸지 않는다.

최신의 의미: 해당 실행에서 검증에 성공한 DART 응답과 일치한다는 뜻이다. 원격 서버의 지속적인 최신성, 전체 배치의 동일 시점 스냅샷, 모든 공시의 완전성을 보장한다는 뜻은 아니다. 자동 주기 실행은 이번 범위 밖이다.

## 3. 공시 발견 흐름

공식 문서를 구현 시 확인한다:

- 기업 고유번호: https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019018
- 공시검색: https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019001
- 원본 파일: https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019003

흐름은 stock_code → corp_code → 공시 목록의 rcept_no → 각 원본 수집이다. 종목코드, 기업 고유번호, 접수번호는 서로 다른 문자열 식별자다. 종목코드가 없는 기업도 corp_code 직접 입력으로 처리할 수 있게 한다.

- stock_code와 corp_code 입력은 둘 중 하나를 받는다. 기업명 퍼지 검색은 이번에 하지 않는다.
- 종목코드는 공식 기업 고유번호 자료로 매핑한다. 매핑 자료의 취득시각을 기록하고 갱신 방법을 제공한다. 해소 실패/복수 후보는 임의 선택하지 않는다.
- 기간은 접수일 범위다. 분석 사업연도와 구분한다. FY2025 보고서가 2026년에 접수될 수 있으므로 끝 날짜를 2025년으로 강제하지 않는다.
- 이번 기본 공시 유형은 정기공시다. 사업·반기·분기 및 관련 정정을 포함하고 반환된 실제 유형/보고서명은 보존한다.
- last_reprt_at=N으로 제출·정정 목록을 보존한다. 모든 페이지를 확인하고 rcept_no로 중복 제거한다.
- 조회 범위·필터·시각·원본 목록 항목을 manifest에 기록한다. 회사·보고서명·접수일은 제공값을 보존하고, report_fiscal_year를 접수일에서 추측하지 않는다.
- 목록이 정상적으로 비어 있는 것과 API 오류·페이지 수집 실패를 구분한다. 일부 페이지만 받은 실행을 complete로 기록하지 않는다.
- manifest를 만든 뒤 원본 수집 대상을 정한다. 제한 실행을 위한 max-filings 등 작은 실행 상한을 제공하고, 상한으로 미처리된 항목을 실패/완료와 구분한다.
- 동일 실행에서 목록 중복 때문에 같은 원본을 여러 번 다운로드하지 않는다. 다음 실행에서는 다시 원격 확인한다.
- 첫 실 API 검증은 작은 기간과 적은 건수로 수행한다. 사용자가 선택하지 않은 전체 시장 대량 다운로드를 자동으로 시작하지 않는다.

기존 접수번호 CLI는 유지하고 기업·기간 수집 진입점을 추가한다. 정확한 명령 이름과 옵션은 저장소 구조에 맞게 정하되 README에 PowerShell 예제를 제공한다. API 키는 환경변수로만 받는다.

## 4. 원격 확인 결과 계약

HTTP 성공과 수집 성공을 분리한다. 성공 원본은 ZIP 바이너리이며 XML API 오류·빈 응답·손상 ZIP을 최신 원본으로 저장하면 안 된다. 기존 크기·timeout·비밀키 보호 정책을 유지한다.

초기 구현에서는 원본을 실제로 다운로드해 SHA-256을 계산한다. DART의 ETag/Last-Modified/304 지원을 가정하거나 HEAD 응답만으로 내용 동일성을 주장하지 않는다. 조건부 요청 최적화는 검증 전 도입하지 않는다.

| 상태 | 의미 | 동작 |
|---|---|---|
| created | 이 접수번호의 최초 정상 관측 | 원본/메타데이터 저장, 현재 버전 지정 |
| unchanged | 정상 로컬 현재 버전과 새 원격 ZIP 바이트가 같음 | 원본 중복 저장 없음, 성공 확인 시각·실행 기록 갱신 |
| updated | 정상 로컬 현재 버전과 새 원격 ZIP 바이트가 다름 | 과거 원본 보존, 새 버전 저장 후 현재 참조 전환 |
| repaired | 로컬 원본/메타데이터가 손상됐고 정상 원격 응답으로 복구 성공 | 손상 상태 기록·격리, 정상 원본 복구; unchanged로 숨기지 않음 |
| failed | 원격 확인 또는 검증/저장 실패 | 이전 정상 원본 보존, 현재 확인 실패 기록 |

상태 이름은 동등한 의미가 유지되면 기존 코드 관례에 맞춰 조정 가능하다.

비교 대상은 ZIP 원본 바이트다. SHA-256은 공시 식별자가 아니며 저장 바이트 비교/무결성 확인 수단이다. 내용상 같은 문서도 ZIP 포장 차이로 해시가 달라질 수 있으므로 updated를 '공시 본문 정정 확인'으로 표현하지 않는다. 의미 수준 diff는 이후 파싱 단계의 과제다.

같은 접수번호의 원본 바이트 변화와 별도 접수번호로 제출된 정정공시는 구분한다. 후자는 별도 filing으로 수집한다. 제목만 보고 정정 관계를 확정하지 않는다.

과거 저장 버전과 동일한 바이트로 되돌아온 경우 정상 과거 파일을 재사용할 수 있다. 관측 이력에는 새 확인을 남기고 현재 참조를 그 버전으로 바꾼다.

## 5. 저장·확인 이력·실패 복구

구체적인 디렉터리/DB 구조는 맡긴다. 이번 규모에 DB·분산 작업 시스템을 새로 도입할 필요는 없다. 보장해야 할 것은 다음이다.

- 공시 식별: source + receipt_no.
- 원본 버전: 해당 공시의 원본 SHA-256, 바이트 수, 실제 원본, 취득시각.
- 현재 참조: 마지막으로 성공적으로 확인한 원본 버전.
- 확인 이력: run_id, receipt_no, 시작/완료 시각, 결과, 관측한 해시, 안전하게 정리한 오류 유형.
- 성공 확인 시각과 최근 시도 시각을 구분한다. 실패했다고 성공 확인 시각을 갱신하지 않는다.
- unchanged일 때 원본 최초 취득시각을 덮어쓰지 않는다. 원격 확인 시각만 갱신한다.
- 파일과 메타데이터가 완성되기 전에 현재 참조를 바꾸지 않는다. staging → 검증 → 버전 확정 → 현재 참조 전환이라는 의미를 보장한다.
- 이전 정상 버전을 파괴하지 않는다. 저장 중 중단돼도 이전 또는 새 정상 버전을 가리키도록 설계한다. 로그를 정상 완료 판단의 유일한 근거로 삼지 않는다.
- 현재 참조와 실행 기록 사이의 중단 가능성도 고려하고, 재실행에서 불완전 상태를 식별할 수 있게 한다. 여러 파일 쓰기를 각각 원자적으로 했다는 이유만으로 전체 트랜잭션이 원자적이라고 주장하지 않는다.
- 이번 실행 범위에 단일 작성자 전제를 명시하거나 최소한의 실행 잠금을 둔다. 분산 동시성 지원을 구현했다고 주장하지 않는다.
- 기존 TASK-001 저장 결과를 읽을 수 있게 한다. 형식 전환 시 기존 원본을 보존하고 과거 데이터를 원격 확인된 것으로 허위 승격하지 않는다. 새 정책의 첫 성공 확인은 실제 재다운로드가 필요하다.
- API 오류, 원격 파일 없음, 목록에서 사라짐을 이유로 로컬 이력을 자동 삭제하지 않는다. 확인한 상태와 과거 보관을 구분한다.

## 6. 배치와 오류 처리

일단 순차 처리로 시작한다. 전체 기업·스케줄러·고동시성 최적화는 하지 않는다.

일시적인 네트워크/서버 오류만 제한된 재시도와 backoff를 허용한다. 재시도 횟수·timeout을 명시하고 인증 오류·잘못된 입력은 재시도하지 않는다. 요청 제한 응답을 받으면 반복 호출을 중단하고 아직 처리하지 않은 대상을 기록한다.

개별 문서 오류가 있더라도 실행 요약을 남긴다. 치명적 인증/요청 제한 문제는 배치를 중단하고, 나머지 개별 오류는 가능한 범위에서 다음 문서로 진행한다. 실행 결과에서 목록 조회 완료 여부, 선택 건수, 처리 건수, created/unchanged/updated/repaired/failed/미처리 건수를 구분한다. 실패나 상한 중단을 전체 동기화 성공이라고 표시하지 않는다.

## 7. 검증과 완료 조건

테스트 코드를 기계적으로 늘리지 말고 아래 계약을 확인하는 테스트를 작성한다.

- 기업 매핑과 목록 페이지네이션으로 접수번호가 자동 전달됨.
- 정상 빈 목록, 중복 항목, 페이지 실패가 각각 구분됨.
- 정상 로컬 파일이 있어도 실제 원격 요청을 수행함.
- 동일 원격 바이트: 원본 버전 수 불변, 확인 이력/시각 갱신.
- 다른 원격 바이트: 이전 버전 보존, 새 현재 버전 지정.
- 원격 오류/손상 ZIP: 이전 정상 파일과 현재 참조 유지, 성공 확인 시각 유지.
- 로컬 손상+원격 정상: 복구 결과가 기록됨.
- 저장 중단: 부분 결과가 현재 정상 버전으로 노출되지 않음.
- 새 정정 접수번호: 기존 공시를 덮어쓰지 않고 별도 처리.
- 기존 TASK-001 형식: 안전하게 전환하고 실제 원격 확인 전 최신 표시하지 않음.
- 로그·메타데이터·HTTP 예외에 인증키가 노출되지 않음.

uv로 테스트·lint를 실행하고 실제 결과를 보고한다. 키가 있으면 적은 건수로 온라인 검증을 하되 키를 채팅에 요구하거나 출력하지 않는다. 실 API에서 원본 변화 사례가 없으면 변경 시나리오는 모킹으로 검증했다고 명시한다. 모든 성공을 실환경에서 재현했다고 주장하지 않는다.

## 8. 범위 밖

본문 파싱·청킹·검색 색인·LLM 연결·웹 UI·로그인·클라우드 배포·전체 시장 일괄 실행·정정 본문 diff·주기적 스케줄러는 이번 작업에 포함하지 않는다. 이 정책은 에이전트가 검색을 선택한다는 제품 설계와 별개인 수집 계층의 동기화 정책이다.

## 9. 구현 후 인계

README와 저장소 내 TASK-001 관련 현재 사용 안내에서 폐기된 '로컬 정상이면 온라인 확인 없이 skip' 정책을 바로잡는다. 과거 작업 기록은 변경 이력으로 남길 수 있지만 현재 정책과 혼동되지 않게 한다. 이 지시서를 docs/tasks/에 기록하고 정책 변경 이유를 작업 기록에 남긴다.

최종 보고는 코드 전체 복사 대신 다음을 포함한다:

1. 구현된 사용자 흐름과 정책 변경 요약.
2. CLI 실행 예시와 변경 파일.
3. 테스트 결과 및 실 API 검증 여부.
4. 동일 원본·원본 변경·원격 실패 시 실제 저장 결과의 차이.
5. 알려진 한계와 코드 리뷰에서 우선 확인할 사항.
6. 커밋 메시지/PR 설명 초안. 기존 Git 작업을 보존하며 자동 push·merge는 별도 요청 없이는 하지 않는다.

사용자는 이 작업 다음에 코딩 에이전트와 코드 리뷰를 진행한다. 파일별 세부 학습 질문에 대한 답변을 구현 진행 조건으로 요구하지 않는다.
