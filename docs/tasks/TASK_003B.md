## Cursor 전달용 — TASK-003B

TASK-003의 기본 설계를 유지하면서, 청킹 전에 원문 충실도와 결과 재사용 계약을 보완해 주세요. 먼저 저장소 지침과 실제 코드·테스트·원본을 확인하고, 아래 우려가 이미 해결되어 있으면 불필요하게 다시 구현하지 말고 근거를 보고해 주세요.

### 배경과 범위

이 프로젝트는 국내 공시 리서치 에이전트입니다. 현재 수집은 원격 ZIP을 재검증하고 원본 버전을 보존합니다. 파서는 저장된 ZIP의 SHA-256을 고정해 dart4 XML 제목·문단·표를 추출합니다. 원격 동기화와 파싱의 책임 분리를 유지하세요.

이번 작업에서는 수집 배치 확장, HTML/OCR, 청킹, 임베딩, 계정 매핑, LLM 추정, UI를 구현하지 않습니다. 모호한 문서 역할과 사업연도는 unknown으로 두어도 됩니다.

### 1. XML 전처리의 안전성과 추적 가능성

- 현재 “알려진 태그 밖의 `<`와 bare `&`를 이스케이프”하는 구현을 검사하세요. 알 수 없는 정상 태그를 일반 텍스트로 바꾸고 success로 처리하는 경로가 있는지 확인하세요.
- 관측된 리터럴 `<신설>` 같은 안전하게 식별 가능한 보정과 미지원 XML 구조를 구분하세요. 알 수 없는 구조를 모두 문자로 간주하는 일반 규칙은 피하세요. 확신할 수 없는 구조는 경고와 partial/unsupported/failed 중 계약에 맞는 상태로 드러내세요.
- 속성·텍스트·주석·CDATA·이미 이스케이프된 엔티티 등 문맥을 보존하세요. 특히 이중 이스케이프와 미지원 자식 태그의 묵시적 누락을 검사하세요.
- 원본 ZIP은 수정하지 마세요. 보정 규칙 버전, 적용 규칙·건수 및 변경 위치와 전후 내용을 재확인할 수 있는 기록을 남기세요. 별도 보정 리포트를 써도 됩니다. 바이트 위치가 아니면 위치 체계를 명시하세요.
- 안전하다고 확인한 보정이 있었다는 이유만으로 무조건 partial로 만들 필요는 없습니다. 의미 보존이 불확실한 경우와 구분하고 기준을 문서화하세요.
- DOCTYPE 거부 등 기존 안전장치를 유지하세요. ZIP 경로 이탈 및 비정상 팽창 제한이 이미 있는지도 확인하고, 없다면 해당 입력 경계를 보호하는 최소한의 제한을 추가하세요.

### 2. 독립적인 원문 충실도 검증

- 기존 25개 locator 대조가 전처리 이후 동일 트리의 왕복 검증인지 확인하고 검증 범위를 정확히 기록하세요.
- 그 검증을 유지하되, 전처리 전 원본에서 사람이 확인한 내용으로 기대값을 작성하는 별도 검증을 추가하세요. 파서 출력이나 동일 전처리 결과로 기대값을 자동 생성하지 마세요.
- 원본 → 출력의 누락 확인과 출력 → 원본의 일치 확인을 함께 하세요. 보정된 구간, 인라인 텍스트, 공백·부호·괄호·단위, 병합 표, 중첩 표, 알 수 없는 태그를 포함한 작은 대표 표본으로 충분합니다.
- 원본 버전·멤버·확인 위치·기대 내용·실제 결과를 검토 기록에 남기세요. 최신 웹 문서와 비교하는 경우 동일 버전임을 보장할 수 없으므로 저장된 원본을 기준으로 삼으세요.
- 빈 표는 대표 표본에서 자식 표·텍스트·이미지 참조 유무도 확인하세요. 모든 빈 표를 삭제하는 변경은 하지 마세요.

### 3. 완료 결과와 캐시 재사용

- COMPLETE는 산출물 쓰기 완료, manifest 상태는 파싱 품질이라는 의미를 분리하세요. partial 종료 코드 0은 유지 가능하지만 다음 단계에서 완전 성공으로 간주하면 안 된다고 명시하세요.
- 완료 결과 재사용 전에 필수 파일의 존재·읽기 가능성·무결성 및 원본 SHA, 파서/전처리 버전, 전체 config hash, 스키마 일치를 확인하세요. 기존 해시 검증 방식이 있으면 활용하세요.
- 경로가 config hash 앞 16자를 사용하므로 manifest의 전체 해시가 다르면 같은 결과로 재사용하지 마세요.
- 손상 결과는 재사용하지 말고 기록·격리 후 안전하게 재생성하거나 명시적으로 실패시키세요. 부분 작성물이 정상 완료물로 보이지 않게 하세요.
- 완료된 partial의 재사용 자체는 허용합니다. 재사용해도 partial을 유지하고 경고를 잃지 마세요.
- 후속 검색 파이프라인의 기본 계약은 COMPLETE만 확인해 입력을 받지 않는 것입니다. 초기에는 partial을 자동 수용하지 않으며, 향후 영향 없는 멤버·요소만 수용하는 별도 품질 정책을 도입할 수 있다고 명시하세요. 아직 검색 코드가 없으면 해당 계약 문서화까지만 하세요.

### 4. 버전과 회귀 검증

- 출력·전처리 동작이 달라지면 파서 버전 또는 명시적으로 식별되는 변환 버전을 변경해 이전 캐시를 잘못 재사용하지 않게 하세요. 기존 원본과 이전 파싱 결과는 보존하세요.
- 실제 남은 위험을 겨냥한 최소 테스트를 추가하세요: 미지원 태그의 묵시적 성공 방지, 보정의 의미 보존과 이중 이스케이프 방지, COMPLETE가 있지만 출력이 손상된 경우, 전체 설정 해시 불일치, partial 재사용 상태 유지.
- 기존 테스트와 문서에 안내한 lint 명령을 실행하세요. README의 `ruff check .`와 작업 로그의 `ruff check src tests`가 다르면 실제 검증 범위를 맞추거나 차이를 설명하세요.
